## はじめに：サービス名は覚えたのに、組み合わせで手が止まる

サービス名は覚えたのに、組み合わせの問題になると手が止まる。

そんな経験はありませんか。

GuardDutyとSecurity Hub、ConfigとCloudTrail。

どっちを選ぶのか分からない。

1つだけなら解けるのに、組み合わせになると順番が分からなくなる。

この記事はドメインの記事ではありません。

ドメインをまたぐ7つの「型」の特集です。

核は1つだけです。

「何のサービスか」ではなく、「いつ・どこで・どの順番で使うか」で見る。

この視点があれば、組み合わせ問題は怖くありません。

:::message
この記事に出てくる問題パターンは、すべて私が学習用に自分の言葉で再構成したものです。
本番試験の問題文や選択肢そのものは掲載していません。
:::

## まず切り分け：7つの型を一覧で見る

7つの型は、どれも「流れ」か「分け方」の話です。

| 型 | 見るもの | 核 |
| --- | --- | --- |
| ①検出→修復 | 流れ | 検知・つなぐ・直す・知らせる |
| ②CI/CD | 流れ | ソースからデプロイまで |
| ③統制 | 層 | 予防・検出・配布・監査 |
| ④ログ集約 | 目的 | 集めるか、見るだけか |
| ⑤DR | 範囲 | AZか、リージョンか |
| ⑥セキュリティ | 対象 | 何を守るかで分ける |
| ⑦配信 | 通信 | プロトコルで分ける |

ここでは「いつ・どこで・どの順番で使うか」だけを見ます。

## パターン1：検出→通知→自動修復 ― 4役の流れを覚える

**引き金**：「セキュリティグループに0.0.0.0/0が追加されたら、自動で削除したい」。

| 役 | 担当 |
| --- | --- |
| 検出 | Configルール／GuardDuty |
| つなぐ | EventBridge |
| 直す | SSM Automation／Lambda |
| 知らせる | SNS |

即答は、この順番そのものです。

検出はConfigルールやGuardDutyです。

EventBridgeが修復へ回します。

直すのはSSM Automationです。

修復はSSMのドキュメントにひもづけ、最後にSNSで知らせます。

Configは「検知」だけで、直す機能はありません。

CloudWatchアラームも「知らせる」だけで、直しません。

「検知したサービスに直させる」は、即✕です。

:::message
自動修復は「戻しても安全なもの」だけに絞ります。
:::

## パターン2：CI/CDパイプライン ― 順番と承認の位置

**引き金**：「ソース変更→ビルド→テスト→承認→デプロイを自動化したい」。

| 段階 | 担当 |
| --- | --- |
| ソース | CodeCommit／GitHub／S3 |
| ビルド | CodeBuild |
| テスト | CodeBuild（別ステージ） |
| 承認 | Manual Approval |
| デプロイ | CodeDeploy／CloudFormation |

全体を握るのはCodePipelineです。

ビルドだけならCodeBuild、デプロイだけならCodeDeploy。

見るのは、順番と承認の位置です。

承認はデプロイの直前です。

テストの前やない。

本番へ行く最後の関門です。

テストはビルドと別ステージです。

重いテストは待たせずに並べます。

①SDLC自動化区の問題3の型です。

## パターン3：マルチアカウントガバナンス ― 5つの層で見る

**引き金**：「組織全体に同じルールを、新しいアカウントにも自動で」。

| 層 | 担当 |
| --- | --- |
| 基盤 | Organizations＋OU |
| ガードレール | SCP（予防）＋Config（検出） |
| 配布 | StackSets／CfCT |
| アクセス | Identity Center |
| 監査 | 組織トレイル＋Aggregator |

予防はSCP、検出はConfigルールです。

SCPは上限を決めるだけで、許可は与えません。

配るのはStackSets、新規への自動適用はCfCTです。

組織トレイルは、全アカウントの操作ログを1つのS3へ集めます。

Aggregatorは、全アカウントの準拠を1画面で見せます。

Aggregatorは「見るだけ」です。

ルール配布も修復もできません。

配るのは組織適合パックかStackSetsです。

「Aggregatorでルールを配る」は、即✕です。

タグとコストもこの層です。

タグポリシーで型をそろえ、一括請求でまとめます。

## パターン4：ログ・監視の集約 ― 集めるか、見るだけか

**引き金**：「複数アカウントのログとメトリクスを、1か所で見たい」。

| 型 | やり方 | 向くもの |
| --- | --- | --- |
| データを集める | 送信先＋Firehose→S3 | 長期保存・分析 |
| 見るだけ | クロスアカウント監視 | 日々の監視・ダッシュボード |

即答は、目的で分けることです。

長期保存や監査・分析なら、データを集めます。

集中管理アカウントの送信先から、FirehoseでS3へ流します。

日々の監視なら、見るだけで十分です。

クロスアカウントオブザーバビリティで、データは動かさず横断で見ます。

Organizations連携なら、新規アカウントも自動で参加します。

分析はLogs InsightsかAthenaです。

アラートはアラーム→EventBridge→SNS、トレースはX-Rayです。

S3＋Athenaの手作りは、ログしか運べません。

## パターン5：DR／高可用性 ― AZか、リージョンか

**引き金**：「リージョンが丸ごと落ちても、サービスを止めたくない」。

「高可用性」はAZの話、「DR」はリージョンの話です。

Multi-AZはDRやない。

| 要件 | 構成 |
| --- | --- |
| RDS高可用性 | Multi-AZ（自動フェイルオーバー） |
| RDSのDR | クロスリージョンリードレプリカ |
| AuroraのDR | Global Database |
| EC2高可用性 | Auto Scaling＋ALB＋Multi-AZ |
| S3データ保護 | CRR＋バージョニング |
| 切り替え | Route 53＋ヘルスチェック |

先に決めるのは「AZか、リージョンか」です。

Multi-AZはAZ障害の自動フェイルオーバーで、リージョン障害には届きません。

リージョンをまたぐには複製が要ります。

Global Databaseはストレージ層で複製します。

遅延1秒未満、昇格1分未満、セカンダリ最大10リージョンです。

CRRは両方のバケットでバージョニングが必須です。

既存のオブジェクトは複製されません。

後からはBatch Replicationです。

切り替えはRoute 53のヘルスチェックです。

不健康ならセカンダリを返します。

DNSの切り替えはTTLの影響を受けます。

即時ならGlobal Acceleratorです。

:::message
原典は「最大5リージョン」でした。
2025年5月に緩和され、今は最大10リージョンです。
:::

## パターン6：セキュリティサービスの使い分け ― 守るもので分ける

**引き金**：「脅威を検出したいのに、どのサービスか分からない」。

| 守るもの・検出するもの | サービス |
| --- | --- |
| アクセス制御・認証 | IAM／Identity Center |
| 権限の制限 | SCP |
| 脅威検出 | GuardDuty |
| 脆弱性スキャン | Inspector |
| 機密データ検出 | Macie |
| 準拠チェック | Configルール |
| 全体の可視化 | Security Hub |
| 暗号化・シークレット | KMS／Secrets Manager |
| API監査 | CloudTrail |
| DDoS防御 | Shield／WAF |
| 調査 | Detective |

「何を検出・守るか」の名詞で分けます。

GuardDutyは脅威、Inspectorは脆弱性、Macieは機密データです。

3つとも「検出」ですが、見るものが違います。

Security Hubは集約の道具です。

結果を1か所に集め、基準と照らします。

自分で脅威は見つけません。

検出→集約→調査の流れです。

GuardDutyが検出して、Security Hubへ集約します。

調査はDetectiveです。

GuardDutyは「検出」だけやから、攻撃は止めません。

止めるのは修復側です。

SSM AutomationやLambda、WAFへつなぎます。

パターン1と同じ型です。

## パターン7：グローバルトラフィック配信 ― プロトコルで分ける

**引き金**：「世界中から速く、止まらずに届けたい」。

| シナリオ | 構成 |
| --- | --- |
| TCP/UDP×超低レイテンシー | Global Accelerator＋NLB |
| HTTP(S)動的×グローバル配信 | CloudFront＋ALB |
| HTTP(S)×DNSで十分 | ALB＋Route 53レイテンシー |
| 静的＋動的の混在 | CloudFront（オリジンALB） |

プロトコルを先に見ます。

HTTP／HTTPSでキャッシュできるなら、CloudFrontです。

エッジにキャッシュし、静的コンテンツを近くから返します。

TCP／UDPや固定IPが必要なら、Global Acceleratorです。

2つの静的Anycast IPで、バックボーンへ乗せます。

キャッシュはしません。

ヘルスチェックでフェイルオーバーします。

DNSのキャッシュは待ちません。

DNSで十分なら、Route 53のレイテンシールーティングです。

近いリージョンを返し、不健康な方を外します。

「速くする＝CloudFront」が罠です。

ゲームやVoIP、MQTTといった非HTTPには使えません。

## 反射ドリル：横断パターン8行

横断パターンの反射ドリルです。

左の引き金を見て、右の即答が口から出るまで回します。

| 引き金 | 即答 |
| --- | --- |
| 検出→直す→知らせる | Config→EventBridge→SSM→SNS |
| Configが非準拠を検出 | 直すのはSSM Automation |
| ソース→ビルド→テスト→承認 | CodePipeline。承認は直前 |
| 組織全体＋新規も自動 | SCP＋Config＋StackSets |
| 全アカウントの準拠を1画面で | Aggregator（見るだけ） |
| 複数アカウントを1か所で監視 | クロスアカウント監視 |
| リージョン障害でも止めない | 複製でまたぐ。Multi-AZはDRではない |
| 脅威・脆弱性・機密データ | GuardDuty・Inspector・Macie |
