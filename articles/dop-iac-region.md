## はじめに：成功したのに、Lambdaが古いまま

CloudFormationでデプロイが成功したのに、Lambdaの中身が古いままだった。

そんな経験はありませんか。

成功と表示されるのに、動いているのは古いコード。

この地方のボスは、そんな「成功したのに変わらない」罠で揺さぶってきます。

②IaC・設定管理区の出題比率は17％。

核になる考え方は3つです。

「テンプレートの文字面しか見ない」「ズレは検出だけで直さない」「配る道具と縛る道具は別」。

この3つを押さえれば、この地方は読みやすくなります。

:::message
この記事に出てくる問題パターンは、すべて私が学習用に自分の言葉で再構成したものです。
本番試験の問題文や選択肢そのものは掲載していません。
:::

## まず切り分け：4つの動詞で分ける

この地方の土台は、道具の役割分担です。

「何をしたいか」の動詞で分けます。

| やりたいこと | 選ぶもの |
| --- | --- |
| インフラをコードで作る | CloudFormation |
| 全アカウントへ配る | StackSets |
| 新規アカウントにも自動で | CfCT |
| パッチや設定の運用 | SSM |

コードで書きたいならCDKです。

CDKは書いたコードをCloudFormationに変換して動かします。

試験ではCloudFormationを直接使う問題のほうが多いです。

## ボス1：S3同一Keyの差分罠 ― 成功したのに更新されない

**引き金**：スタック更新は成功したのに、Lambdaの関数が更新されない。

CodePipelineからCloudFormationでデプロイしたとします。

LambdaのコードはS3に置いたZIPです。

新しいZIPを同じキーで上書きして、スタックを更新する。

結果は「更新成功」。

でも関数は古いままです。

| ステップ | 内容 |
| --- | --- |
| **最終文** | 聞かれているのは「更新されない原因」です |
| **制約** | 決め手は「同じS3キーに上書きした」という事実 |
| **違反スキャン** | 権限やロール不足の選択肢は、エラー種別が違う → 消去 |

原因は、CloudFormationの見方にあります。

CloudFormationはテンプレートの文字面しか見ません。

S3の中身が変わっても、テンプレートは変わりません。

キーとバージョンが同じなら、「変更なし」と判断します。

公式ドキュメントにも、はっきり書かれています。

S3のデプロイパッケージの変更は、スタック更新時に自動では検出されない。

関数コードを更新するには、テンプレートのオブジェクトキーかバージョンを変えること。

即答は3つのうちどれかです。

| 対策 | やり方 |
| --- | --- |
| バージョニング＋バージョン指定 | S3バージョニングを有効化し、`S3ObjectVersion` を指定する |
| キーを毎回変える | ファイル名にハッシュや日時を入れて新しいキーにする |
| SAMに任せる | `sam build` ならハッシュ付きの新キーで差分が生まれる |

変更セットを作れば、差分が無いことが実行前に分かります。

この罠に気づく手がかりになります。

同じ原理は、ECSのイメージタグにもあります。

`latest` のような動く名前で中身だけ更新すると、差分検知に負けます。

解は常に「参照を一意にする」です。

:::message
手動で `update-function-code` を叩いて直すと、テンプレートと実態がズレます。
それがドリフトの原因になります。
:::

## ボス2：ドリフト検出の罠2連 ― 検出はする、直さない

**引き金**：ConfigルールはNON_COMPLIANT。

でもコンソールはIN_SYNCと表示する。

ドリフト検出は「ズレを見つける」だけの道具です。

直す機能はありません。

ここを混ぜると負けます。

| ステップ | 内容 |
| --- | --- |
| **最終文** | 聞かれているのは「この食い違いをどう読むか」です |
| **制約** | 決め手は「コンソールはIN_SYNC」という事実 |
| **違反スキャン** | 「ルールが正しい」前提の選択肢は消える |

まず、ドリフト検出の対象外を知っておきます。

カスタムリソースは、ドリフト検出の対象外です。

対象外のリソースは `NOT_CHECKED` になります。

次に、Configルールの罠です。

ドリフトを自動で検知して知らせる型は、こうです。

Configのマネージドルールがあります。

`cloudformation-stack-drift-detection-check` です。

裏で `DetectStackDrift` を実行します。

違反が出たらEventBridgeが拾い、SNSへ通知します。

ルールが `NON_COMPLIANT` なのに、コンソールは `IN_SYNC`。

この食い違いは、誤検出を疑います。

検出の呼び出しがスロットリングで失敗すると、ルールは既定で `NON_COMPLIANT` になります。

コンソールの `IN_SYNC` が証拠です。

無視してよい、というのが即答です。

「検出」と「修正」を分けるのが、このボスの型です。

| 役割 | 担当 |
| --- | --- |
| ズレを見つける | ドリフト検出／Configルール |
| 知らせる | EventBridge→SNS |
| 直す | 手動修正か、テンプレートの更新 |

## ボス3：CfCT vs StackSets ― 配る道具の層構造

**引き金**：「新規アカウントにも自動で」が要件に入っている。

マルチアカウントの展開は、層で考えます。

| 層 | 担当 | 決め手の言葉 |
| --- | --- | --- |
| アカウントを作る | Account Factory | Control Towerの標準機能 |
| 全アカウントへ配る | StackSets | テンプレートを横展開 |
| 新規にも自動で適用 | CfCT | CFN＋SCPをOUへ自動適用 |
| Terraformで全部やる | AFT | Terraform派の専用窓口 |

StackSetsの自動デプロイが、このボスの中心です。

サービスマネージド型のStackSetで自動デプロイを有効にします。

OUをターゲットに指定するのが条件です。

すると、OUに入った新規アカウントへ自動でスタックが展開されます。

OUを離れたアカウントのスタックは、自動で削除されます。

EventBridge＋Lambdaで自前配管する選択肢は、ここで負けます。

離脱時の自動削除をカバーできないからです。

ここが「自前配管を切る決め手」です。

CfCTは、Control Towerのカスタマイズ専用の仕組みです。

manifestに書くのは、テンプレートとSCPです。

OUやアカウントへ自動で適用されます。

新規アカウントの作成をきっかけに、ライフサイクルイベントで動きます。

「SCP無しならCfCT不要」という切り分けも覚えておきます。

配るだけならStackSetsで足ります。

SCPまで含めて新規アカウントへ自動適用したいとき、CfCTの出番です。

:::details CfCTとAFTの対応表
- CFN派のカスタマイズはCfCT
- Terraform派のカスタマイズはAFT（Account Factory for Terraform）
- 言語が違うので、取り違えに注意です
:::

## ボス4：Patch Managerの3点セット ― 夜間に承認済みだけ当てる

**引き金**：「承認済みパッチのみ」「夜間枠で自動適用」。

パッチの自動化は、3つに分解します。

| ピース | 役割 |
| --- | --- |
| パッチベースライン | 何を当てるか。承認ルールを決める |
| メンテナンスウィンドウ | いつ当てるか。夜間枠を決める |
| AWS-RunPatchBaseline | どう当てるか。Installで実行する |

3つそろって、初めて「承認済みだけを夜間に自動で」が成立します。

| ステップ | 内容 |
| --- | --- |
| **最終文** | 基準は「承認制御」と「夜間枠」の両立です |
| **制約** | スロットは2つ。①承認済みだけ ②夜間枠で自動 |
| **違反スキャン** | `yum update -y` は全パッチ無差別 → ①に違反して消去 |

`yum update -y` は「すべての利用可能なパッチ」を当てます。

承認制御の要件と真っ向から矛盾するので、地雷ワードです。

OS内のcronで回す手作りも、台数が増えると管理が破綻します。

内部パッチリポジトリから配る場合も、型は同じです。

カスタムパッチベースラインで代替パッチソースを内部リポジトリにします。

メンテナンスウィンドウと組み合わせれば、ハイブリッド環境でも同じ3点セットで回ります。

## 反射ドリル：この地方の8行

最後にこの地方の反射ドリルを置いておきます。

左の引き金を見て、右の即答が口から出るまで回すやつです。

| 引き金 | 即答 |
| --- | --- |
| S3同一Keyに上書きして更新 | 差分にならない。バージョン指定かKeyを変える |
| ドリフトを自動検知→即アラート | Configルール＋EventBridge→SNS |
| カスタムリソースのドリフト検出 | 非サポート。対象外になる |
| 全アカウント×全リージョンへ配る | StackSets。自動デプロイを有効化 |
| 新規アカウントにもCFN＋SCPを自動で | CfCT。manifestでOUへ適用 |
| 承認済みパッチのみ夜間枠で自動適用 | ベースライン＋ウィンドウ＋RunPatchBaseline |
| ゴールデンAMIを多数スタックで毎週更新 | Parameter Store＋SSMパラメータ型 |
| EC2ログイン一元化＋ネット遮断 | Session Manager。ポート22は開けない |

※ゴールデンAMIの更新は、週次LambdaでUpdateStackを回します。

テンプレートの値は更新時に自動で最新に解決されます。
