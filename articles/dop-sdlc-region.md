## はじめに：いちばん大きい地方から攻略する

連載の本編、最初に深掘りするのは①SDLC自動化区です。出題比率は22％で、6つの地方の中で最大。ここを取り切れるかどうかで、全体の2割強の行方が決まります。

前回の記事で固めた3スロット法（最終文を先に読む → 制約を最大3つ拾う → 違反スキャンで消す）を、今回は「使う側」に回します。題材は、CodeBuild／CodeDeploy／CodePipelineの3サービス。この地方のボスは、サービス名の紛らわしさで揺さぶってくるやつが多いんです。だからこそ、制約で切る型が効きます。

:::message
この記事に出てくる問題パターンは、すべて私が学習用に自分の言葉で再構成したものです。本番試験の問題文や選択肢そのものは掲載していません。

## まず切り分け：3サービスは「動詞」で分ける

この地方の土台は、3サービスの役割分担です。サービス名ではなく、問題文の動詞で分けます。

| 問われていること | 答えのサービス | 役割 |
| --- | --- | --- |
| ビルドだけ | CodeBuild | コードをビルド・テストする |
| デプロイだけ | CodeDeploy | アプリケーションを配布・切り替える |
| 全体のフロー管理 | CodePipeline | ソース→ビルド→デプロイの流れ全体を管理する |

「ビルドもデプロイも全部まとめて面倒を見たい」という要件なら全体管理のCodePipeline、「デプロイだけを細かく制御したい」ならCodeDeploy。この切り分けが反射で出るようになると、この地方の問題は一気に読みやすくなります。ほんまに、ここが入口です。

ついでに、CodePipelineの「実行の重なり方」も先に押さえておきます。公式ドキュメントで確認した実行モードは3つです。

- **SUPERSEDED（既定）**：新しい実行が、ステージ前で待っている古い実行を追い越す。古い実行はそこで終わる
- **QUEUED（V2のみ）**：実行はキューに並び、順番に1つずつ処理される。追い越しはなし
- **PARALLEL（V2のみ）**：複数の実行が同時・独立に走る。待たない代わりに、ステージのロールバックは使えない

「途中のコミットは全部デプロイしないといけない」ならQUEUED、「最新だけ通ればいい」ならSUPERSEDED、という具合に、要件の言葉からモードが決まります。

## ボス1：ECSデプロイの2方式 ― CodePipeline×ECS

**引き金**：ECSへのデプロイ方式を問われたら、この2択を思い出す。

ECSへのデプロイは、作法が2種類あります。

- **ローリング方式**：CodePipelineのECSデプロイ（標準）で、`imagedefinitions.json`を使ってタスク定義のイメージを差し替える。部品が少なく、軽い
- **Blue/Green方式**：CodeDeployが仕切る。AppSpecファイルでタスク定義と配布先を指定し、ターゲットグループを切り替える。重いが、切り戻しが速い

3スロットで切ると、こうなります。

- **最終文**：基準は「方式の軽さ」か「切り戻しの速さ」か
- **制約**：「ターゲットグループを2つ用意できるか」「テスト用のリスナーで事前確認したいか」
- **違反スキャン**：Blue/Greenには前提条件があります。デプロイコントローラーをCODE_DEPLOYにすること、ALB（またはNLB）＋ターゲットグループ2つ＋本番用リスナーが必須で、テスト用リスナーは任意、という構成です。前提を満たせない選択肢は、その時点で消えます

なお、デプロイの作法はプラットフォームごとに違います。EC2／ECS／LambdaでAppSpecやフックの形が変わるので、「CodeDeployだから全部同じ」と思うと負けます。

## ボス2：AllowTraffic無言死 ― ログが出ないデプロイ失敗

**引き金**：デプロイが失敗しているのに、ログが一切出ていない。

これは私のノートでも印象に残っているパターンです。普通は「スクリプトのエラーを探す」方向に考えますが、反射は逆です。

- **最終文**：聞かれているのは「失敗の原因」です
- **制約**：決め手は「ログが無い」という事実そのもの
- **違反スキャン**：「スクリプトを修正する」「ログ出力を追加する」といった選択肢は、そもそもスクリプトが動いていない状況では意味がない → 消去

残る見立てはこうです。AllowTrafficのような自動イベントは、スクリプトが無いのでログも出ません。つまり「無言」なのは異常ではなく仕様で、本当の原因は手前のALBヘルスチェック設定の誤りを疑う、という順番になります。ログが無いことを「情報が無い」と読むか、「それ自体が情報」と読むか。ここが分かれ目やと思います。

## ボス3：2時間かかるテスト ― パイプラインに待たせない

**引き金**：「2時間かかるテスト」を、パイプラインの中でどう扱うか。

- **最終文**：基準は「パイプラインを止めずに、長時間テストの結果を待つ」こと
- **制約**：数字スロットに「2時間」が入ります
- **違反スキャン**：テストをパイプラインのアクションとしてそのまま待たせる構成は、長時間の待ちに耐える設計ではない → 消去

即答は、**Step Functions＋コールバック**です。テストの実行をStep Functions側に切り出し、終わったらコールバックでパイプラインに結果を返す形にすると、パイプライン本体は長時間の待ちに付き合わずに済みます。「待つ」という仕事を、待つのが得意な側に渡す、という発想です。

## ボス4：CodeDeploy Blue/Green＋テスト後に旧を自動削除

**引き金**：「同一構成の新しいフリートを用意して無停止で切り替え、テストが終わったら旧側を自動で削除したい」。

- **最終文**：基準は「無停止の切替」と「旧側の自動削除」の両立です
- **制約**：スロットは2つ。①新フリート方式であること ②削除まで自動であること
- **違反スキャン**：Beanstalkのローリングはインプレース（既存の入れ替え）なので①に合わない。BeanstalkのBlue/GreenはDNSスワップが手動寄りで②に合わない。OneAtATimeはトラフィックの再ルーティングを刻む設定で、削除の話とは役割が違うので混ぜない

即答は**CodeDeployのBlue/Green**です。元のインスタンス（Original instances）を終了する設定にし、待機時間を置くことで、「切り替えて、様子を見て、時間が来たら旧側が自動で消える」が成立します。

### ついでに：フックの切り分けもプラットフォーム依存

ボス1で触れた「作法が違う」の代表が、CodeDeployのライフサイクルフックです。公式ドキュメントで一覧を確認しました。

- **Lambdaデプロイ**：フックは `BeforeAllowTraffic` と `AfterAllowTraffic` の2つだけ
- **ECSデプロイ**：`BeforeInstall`、`AfterInstall`、`AfterAllowTestTraffic`、`BeforeAllowTraffic`、`AfterAllowTraffic` の5つ
- **EC2／オンプレミス**：`BeforeInstall` や `ValidateService` など、スクリプトを差し込む形の一式

つまり「LambdaデプロイでBeforeInstallフックを使う」という選択肢は、実在しない組み合わせとして消せます。第2記事で書いた「実在しない機能 → 即消去」の実例が、ここにもあるわけです。

## 反射ドリル：この地方の8行

最後に、この地方の反射ドリルを置いておきます。左の引き金を見て、右の即答が口から出るまで回すやつです。

| 引き金 | 即答 |
| --- | --- |
| 「ビルドだけ」「デプロイだけ」「全体のフロー管理」 | CodeBuild／CodeDeploy／CodePipeline |
| CodePipelineでアクションを並列に走らせる | `runOrder` を同値にする |
| 長時間テスト（2時間超） | CodePipelineは待てない → Step Functions＋コールバック |
| CodePipelineの失敗をSlackに通知 | EventBridge（Pipeline FAILED）＋ LambdaでWebhook |
| CodeDeployの自動ロールバック | メトリクス直結は不可。CloudWatchアラームと統合する |

| Lambdaの段階デプロイ | SAM＋CodeDeployのトラフィックシフト。pre／postフック＋アラームで自動ロールバック |
| SAMのカナリア | `Canary10Percent15Minutes` ＋ CodeDeploy ＋ アラームで自動ロールバック |
