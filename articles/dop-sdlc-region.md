## はじめに：いちばん大きい地方から攻略する

連載の本編、最初に深掘りするのは①SDLC自動化区です。
出題比率は22％で、6つの地方の中で最大。
ここを取り切れるかどうかで、全体の2割強の行方が決まります。

前回の記事で固めた3スロット法を使います。
「最終文を先に読む → 制約を最大3つ拾う → 違反スキャンで消す」という型です。
今回は「使う側」に回します。

最初の相手は、名前が似すぎた3サービスです。
CodeBuild／CodeDeploy／CodePipeline。
この地方のボスは、サービス名の紛らわしさで揺さぶってくるやつが多いんです。
だからこそ、制約で切る型が効きます。

:::message
この記事に出てくる問題パターンは、すべて私が学習用に自分の言葉で再構成したものです。本番試験の問題文や選択肢そのものは掲載していません。
:::

## まず切り分け：3サービスは「動詞」で分ける

この地方の土台は、3サービスの役割分担です。
サービス名ではなく、問題文の動詞で分けます。

| 問われていること | 答えのサービス |
| --- | --- |
| ビルドだけ | CodeBuild（ビルド・テスト） |
| デプロイだけ | CodeDeploy（配布・切り替え） |
| 全体のフロー管理 | CodePipeline（流れ全体を管理） |

切り分けの目安はこうです。

| 要件の言葉 | 選ぶもの |
| --- | --- |
| ビルドもデプロイも全部まとめて面倒を見たい | CodePipeline（全体管理） |
| デプロイだけ細かく制御したい | CodeDeploy |

この切り分けが反射で出るようになると、この地方の問題は一気に読みやすくなります。
ほんまに、ここが入口です。

ついでに、CodePipelineの「実行の重なり方」も先に押さえておきます。
公式ドキュメントで確認した実行モードは、次の3つです。

| モード | 動き |
| --- | --- |
| **SUPERSEDED**（既定） | 新しい実行が古い実行を追い越す |
| **QUEUED**（V2のみ） | キューに並び、順番に1つずつ。追い越しなし |
| **PARALLEL**（V2のみ） | 同時・独立に走る。ステージのロールバック不可 |

要件の言葉からモードが決まります。
「途中のコミットは全部デプロイしないといけない」ならQUEUED。
「最新だけ通ればいい」ならSUPERSEDEDです。

## ボス1：ECSデプロイの2方式 ― CodePipeline×ECS

**引き金**：ECSへのデプロイ方式を問われたら、この2択を思い出す。

ECSへのデプロイは、作法が2種類あります。

| 方式 | 中身 |
| --- | --- |
| **ローリング方式** | `imagedefinitions.json` で差し替え。部品が少なく、軽い |
| **Blue/Green方式** | AppSpec＋ターゲットグループ切り替え。重いが、切り戻しが速い |

3スロットで切ると、こうなります。

| ステップ | 内容 |
| --- | --- |
| **最終文** | 基準は「方式の軽さ」か「切り戻しの速さ」か |
| **制約** | TGを2つ用意できるか／テスト用リスナーで確認したいか |
| **違反スキャン** | Blue/Greenの前提を満たせない選択肢は消える |

Blue/Greenの前提は、はっきり決まっています。
デプロイコントローラーは `CODE_DEPLOY`。
ALB（またはNLB）＋ターゲットグループ2つ＋本番用リスナーが必須です。
テスト用リスナーは任意。
この前提を満たせない構成は、その時点で選択肢から消えます。

なお、デプロイの作法はプラットフォームごとに違います。
EC2／ECS／LambdaでAppSpecやフックの形が変わります。
「CodeDeployだから同じ」と思うと負けます。

## ボス2：AllowTraffic無言死 ― ログが出ないデプロイ失敗

**引き金**：デプロイが失敗しているのに、ログが一切出ていない。

私のノートでも印象に残っているパターンです。
普通は「スクリプトのエラーを探す」方向に考えますが、反射は逆です。

| ステップ | 内容 |
| --- | --- |
| **最終文** | 聞かれているのは「失敗の原因」です |
| **制約** | 決め手は「ログが無い」という事実そのもの |
| **違反スキャン** | スクリプト修正系の選択肢は意味がない → 消去 |

残る見立てはこうです。
AllowTrafficのような自動イベントは、スクリプトが無いのでログも出ません。
つまり「無言」なのは異常ではなく仕様です。
本当の原因は、手前のALBヘルスチェック設定の誤りを疑う、という順番になります。

ログが無いことを「情報が無い」と読むか、「それ自体が情報」と読むか。
ここが分かれ目やと思います。

## ボス3：2時間かかるテスト ― パイプラインに待たせない

**引き金**：「2時間かかるテスト」を、パイプラインの中でどう扱うか。

| ステップ | 内容 |
| --- | --- |
| **最終文** | 基準は「止めずに長時間テストの結果を待つ」こと |
| **制約** | 数字スロットに「2時間」が入ります |
| **違反スキャン** | そのまま待たせる構成は、長時間の待ちに耐えない → 消去 |

即答は**Step Functions＋コールバック**です。
テスト実行をStep Functions側に切り出します。
終わったらコールバックでパイプラインに結果を返す形にすると、パイプライン本体は長時間の待ちに付き合わずに済みます。
「待つ」という仕事を、待つのが得意な側に渡す、という発想です。

## ボス4：CodeDeploy Blue/Green＋テスト後に旧を自動削除

**引き金**：「同一構成の新しいフリートを用意して無停止で切り替え、テストが終わったら旧側を自動で削除したい」。

| ステップ | 内容 |
| --- | --- |
| **最終文** | 基準は「無停止の切替」と「旧側の自動削除」の両立です |
| **制約** | スロットは2つ。①新フリート方式であること ②削除まで自動であること |
| **違反スキャン** | Beanstalk系は①②に合わない。OneAtATimeは役割違い |

補足します。
Beanstalkのローリングはインプレースなので、新フリート方式ではありません。
BeanstalkのBlue/GreenはDNSスワップが手動寄りで、削除まで自動になりません。
OneAtATimeはトラフィックの再ルーティングを刻む設定で、削除とは役割が違います。

即答は**CodeDeployのBlue/Green**です。
元のインスタンス（Original instances）を終了する設定にし、待機時間を置きます。
そうすると「切り替えて、様子を見て、時間が来たら旧側が自動で消える」が成立します。

### ついでに：フックの切り分けもプラットフォーム依存

ボス1で触れた「作法が違う」の代表が、CodeDeployのライフサイクルフックです。
公式ドキュメントで一覧を確認しました。

- **Lambdaデプロイ**：`BeforeAllowTraffic` と `AfterAllowTraffic` の2つだけ
- **ECSデプロイ**：`BeforeInstall`、`AfterInstall`、`AfterAllowTestTraffic`、`BeforeAllowTraffic`、`AfterAllowTraffic` の5つ
- **EC2／オンプレミス**：`BeforeInstall`、`ValidateService` など一式

つまり「LambdaデプロイでBeforeInstallフックを使う」という選択肢は、実在しない組み合わせとして消せます。
第2記事で書いた「実在しない機能 → 即消去」の実例が、ここにもあるわけです。

:::message
Lambdaの段階デプロイは、pre／postフック＋アラームで自動ロールバックまで組めます。
:::

最後にこの地方の反射ドリルを置いておきます。
左の引き金を見て、右の即答が口から出るまで回すやつです。

| 引き金 | 即答 |
