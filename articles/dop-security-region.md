## はじめに：管理アカウントでは動いたのに、メンバーでは動かない

管理アカウントでは動いたのに、メンバーアカウントでは動かない。

そんな経験はありませんか。

同じポリシー、同じ操作なのに、片方だけ弾かれる。

このドメインの問題は、そんな「場所によって結果が変わる」罠で揺さぶってきます。

③セキュリティ・統制区の出題比率は17％。

核になる考え方は3つです。

「与える道具と縛る道具は別」「検知と強制は別」「監査は2人1組」。

この3つを押さえれば、このドメインは読みやすくなります。

:::message
この記事に出てくる問題パターンは、すべて私が学習用に自分の言葉で再構成したものです。
本番試験の問題文や選択肢そのものは掲載していません。
:::

## まず切り分け：4つの動詞で分ける

このドメインの土台は、道具の役割分担です。

「何をしたいか」の動詞で分けます。

| やりたいこと | 選ぶもの |
| --- | --- |
| 組織全体で禁止する | SCP |
| 全アカウントにWAFを強制する | Firewall Manager |
| 設定と操作を監査する | Config＋CloudTrail |
| masterへの直pushを止める | IAMの明示Deny |

ここで一番大事なのは、1行目です。

SCPは「禁止する」道具です。

「許可する」道具ではありません。

この区別が、このドメインのすべての出発点です。

## 問題1：SCP総集編 ― 与えない・効かない・Deny最強

**引き金**：「SCPでフルアクセスを許可」「管理アカウントでも縛れるはず」。

SCPの本質は、たった一文です。

SCPは権限を1ミリも与えません。

上限だけを決めます。

| ステップ | 内容 |
| --- | --- |
| **最終文** | 聞かれているのは「SCPで何ができるか」です |
| **制約** | 決め手は「SCP＋許可」という字面 |
| **違反スキャン** | 「SCPで許可する」選択肢は即消去 |

許可を出すのは、IAMポリシーの仕事です。

SCPとIAMの両方で許可されて、初めて操作が通ります。

片方だけでは動きません。

次に、効く範囲です。

SCPはメンバーアカウントにだけ効きます。

管理アカウントには効きません。

だから「管理アカウントでは動いたのに、メンバーでは動かない」。

これがSCPの指紋です。

メンバーのrootユーザーには効きます。

管理者権限を持つユーザーにも効きます。

| 効く相手 | SCPの扱い |
| --- | --- |
| 管理アカウント | 効かない |
| メンバーのroot | 効く |
| メンバーの管理者 | 効く |

最後に、明示Denyです。

明示Denyは最強です。

Allowがあっても、Denyが勝ちます。

条件キーと組み合わせると、SCPはぐっと強くなります。

| 条件キー | 使い方 |
| --- | --- |
| aws:SourceIp | 範囲外からのAPI呼び出しをDeny |
| ec2:MetadataHttpTokens | required以外なら起動をDeny |

`ec2:MetadataHttpTokens` を使えば、IMDSv2必須でないEC2の起動を組織全体でブロックできます。

Configの検知＋自動終了は事後対応です。

「未然にブロック」が要件なら、SCPの出番です。

:::message
SCPのAllowリストに無い操作は、暗黙のDenyになります。
許可リスト型のSCPでは、書き忘れたサービスがそのまま使えなくなります。
:::

## 問題2：Firewall Manager強制 ― 検知はConfig、強制はFMS

**引き金**：「組織全体にWAFを強制適用」。

WAFを1アカウントに付けるなら、WAFだけで足ります。

組織全体に強制するなら、話が変わります。

即答はFirewall Manager一択です。

Configは「検知・記録」までしかできません。

強制はFMSの仕事です。

| ステップ | 内容 |
| --- | --- |
| **最終文** | 聞かれているのは「強制適用の道具」です |
| **制約** | 決め手は「組織全体に」「強制」という言葉 |
| **違反スキャン** | Configだけの選択肢は、強制ができない → 消去 |

FMSを動かすには、3つの前提が必要です。

| 前提 | 内容 |
| --- | --- |
| ①全アカウント参加 | Organizations（全機能有効）に入る |
| ②管理者の委任 | 管理アカウントからFMS管理者を委任 |
| ③Config有効化 | 全アカウント・全リージョンで有効化 |

3つそろって、初めて盾を配れます。

ポリシー作成は、導入後の運用です。

「前提を問う」問題では、ポリシー作成の選択肢は✕です。

動詞で見分けます。

「導入・動作させるのに必要な手順」なら、前提の3点セットを拾います。

:::details FMSポリシーはリージョン単位
Firewall Managerのポリシーはリージョン単位で作ります。
守りたいリージョンごとにポリシーを作る必要があります。
:::

## 問題3：CodeCommit push禁止 ― 守るのはIAM一本

**引き金**：「masterへの直pushを禁止したい」。

CodeCommitに、ブランチ保護の画面はありません。

GitHubのような設定画面を探しても、見つかりません。

アクセス制御は、IAM一本です。

| ステップ | 内容 |
| --- | --- |
| **最終文** | 聞かれているのは「直pushを止める方法」です |
| **制約** | 決め手は「CodeCommit」「master直push」 |
| **違反スキャン** | 「リポジトリのアクセスポリシー」は実在しない → 消去 |

即答は、IAMポリシーでの明示Denyです。

`codecommit:GitPush` を、条件付きでDenyします。

条件キーは `codecommit:References` です。

値は `refs/heads/master` を指定します。

これで、masterへの直pushだけが止まります。

機能ブランチへのpushは、そのまま通ります。

ここで忘れてはいけないのが、`Null` 条件です。

GitPushには、参照を持たない呼び出しもあります。

`Null` 条件が無いと、Denyがすり抜けます。

正しい流れは、機能ブランチ＋PR＋マージです。

masterに直接触る道を閉じて、PRだけを開けておく。

それがこの問題の型です。

:::message
「リポジトリのアクセスポリシー」は、CodeCommitに存在しません。
便利そうな機能名ほど、選ぶ前に実在を疑ってください。
:::

## 問題4：監査コンビ ― 設定と操作は2人1組

**引き金**：「設定を継続的に評価・監査・監視」。

監査の問題は、2人1組で即決です。

ConfigとCloudTrailです。

| 担当 | 見るもの |
| --- | --- |
| Config | 何がどうなってるか（設定） |
| CloudTrail | 誰が何をしたか（操作） |

Configは、リソースの設定状態と変更履歴を記録します。

CloudTrailは、API呼び出しを記録します。

「誰が・何を・いつ」が分かります。

| ステップ | 内容 |
| --- | --- |
| **最終文** | 聞かれているのは「監査の道具」です |
| **制約** | 決め手は「継続的に評価・監査・監視」 |
| **違反スキャン** | 「自動で元に戻す」は動詞がズレる → 消去 |

「自動で元に戻す」は、監査の仕事ではありません。

要件の動詞とズレた選択肢は、即✕です。

このコンビには、応用が2つあります。

1つ目は、CloudTrail常時有効の保証です。

Configルール `cloudtrail-enabled` で追跡します。

違反が出たらEventBridgeが拾い、Lambdaが再有効化します。

5分おきのポーリングは、監査になりません。

証跡が残らないからです。

2つ目は、ログ改ざんの証明です。

CloudTrailのログファイル整合性検証を使います。

ダイジェストファイルとSHA-256の署名連鎖で、改ざんを検出します。

Glacier Vault Lockは、未来の封印です。

過去の潔白は証明できません。

:::details 「証明せよ」と「防げ」の切り分け
- 「改ざんされていないと証明せよ」→ ログファイル整合性検証
- 「これからの変更を防げ」→ Vault Lock
- 「誰が何をしたか」→ CloudTrail
- 「設定がどう変わったか」→ Config
:::
