## はじめに：成功したはずなのに、古い画面が出る

デプロイは成功したのに、古い画面が出る。

キューが詰まっているのに、エラーはゼロ。

そんな経験はありませんか。

片方は「成功」の報告、もう片方は沈黙の行列。

このドメインの問題は、そんな「見た目と中身のズレ」で揺さぶってきます。

④回復力・自己治癒区の出題比率は15％。

核になる考え方は3つです。

「壊れる前提で作る」「詰まりは数で読む」「大きい荷物は置き場を分ける」。

この3つを押さえれば、このドメインは読みやすくなります。

:::message
この記事に出てくる問題パターンは、すべて私が学習用に自分の言葉で再構成したものです。
本番試験の問題文や選択肢そのものは掲載していません。
:::

## まず切り分け：4つの動詞で分ける

「何をしたいか」の動詞で分けます。

| やりたいこと | 選ぶもの |
| --- | --- |
| デプロイを切り替える | ローリングかBlue/Green |
| 行列の詰まりを読む | 可視性タイムアウト×6 |
| 毒メッセージを隔離する | DLQ＋maxReceiveCount |
| 大きい荷物を運ぶ | S3参照渡し |

ここで一番大事なのは、1行目と2行目です。

切り替え方と、行列の読み方です。

この2つが、このドメインのすべての出発点です。

## 問題1：ローリング vs Blue/Green ― 新旧混在は罠のサイン

**引き金**：「デプロイ成功なのに新旧混在」「切り替えを一括で即時に」。

標準デプロイはローリングです。

Blue/GreenはCodeDeploy経由です。

| 切り替え方 | 仕組み |
| --- | --- |
| ローリング | 既存の台を順に更新する |
| Blue/Green | 新環境を用意して切り替える |

ローリングは、更新中ずっと新旧が混ざります。

だから「成功したのに古い画面が出る」は、まずローリングを疑います。

Blue/Greenは、切り替えの瞬間まで旧環境が残ります。

巻き戻しは、切り戻すだけです。

ローリングの巻き戻しは、旧リビジョンの再デプロイです。

即時性が違います。

| 比較の軸 | ローリング | Blue/Green |
| --- | --- | --- |
| 更新する場所 | 既存の台 | 新しい環境 |
| 切り替え | 徐々に | 一括で即時 |
| 巻き戻し | 再デプロイ | 切り戻し |

次に、ローリング最大の罠です。

デプロイ中にスケールアウトが起きると、新しい台が参加します。

その台には「最後に成功した旧リビジョン」が自動で入ります。

デプロイは成功報告なのに、台数が増えて新旧が混在する。

これがこの問題の指紋です。

対策は1つです。

デプロイ中はスケーリングを一時停止します。

| ステップ | 内容 |
| --- | --- |
| **最終文** | 聞かれているのは「切り替え方の選択」です |
| **制約** | 決め手は「新旧混在」「一括即時」という言葉 |
| **違反スキャン** | 「DNS切替で即時」はTTLで負ける → 消去 |

ALBのBlue/Greenを一括で即時に切り替えるなら、リスナーの転送先を変えます。

ターゲットグループの付け替えです。

Route 53のDNS切替では、即時になりません。

TTLが残るからです。

:::message
CodeDeployのBlue/Greenでは、切り替え前の掃除はグリーン側で行います。
BeforeAllowTrafficフックがその場所です。
BeforeBlockTrafficはブルー側のフックなので、掃除には使えません。
:::

半数ずつ切り替えるなら、CodeDeployDefault.HalfAtATimeです。

:::details ローリングとBlue/Greenの使い分け
- 「既存の台で十分・コストを抑えたい」→ ローリング
- 「切り戻しを一瞬で・新旧を混ぜたくない」→ Blue/Green
- 「ECSでBlue/Green」→ CodeDeploy経由
:::

## 問題2：SQS可視性タイムアウト×6 ― 見えない時間の読み方

**引き金**：「同じメッセージが2回処理される」「行列が伸びるのにエラーは無い」。

可視性タイムアウトは、メッセージの「見えない時間」です。

処理中のメッセージは、他の処理から隠れます。

時間が切れると、再び見えるようになります。

公式の目安は、たった1つです。

可視性タイムアウトは、関数のタイムアウトの6倍以上にします。

バッチウィンドウを使うなら、その分も足します。

| 関数のタイムアウト | 可視性タイムアウトの目安 |
| --- | --- |
| 30秒 | 180秒以上 |
| 5分 | 30分以上 |

関数が30秒で、バッチウィンドウが5秒なら、185秒です。

6倍の理由は、再試行の余白です。

Lambdaはスロットリング時に内部で再試行します。

その間も、メッセージは隠れたままにします。

| ステップ | 内容 |
| --- | --- |
| **最終文** | 聞かれているのは「見えない時間の長さ」です |
| **制約** | 決め手は「可視性タイムアウト」「6倍」という数字 |
| **違反スキャン** | 「短縮して回転を速く」は二重処理 → 消去 |

短くすると、処理中にメッセージが再表示されます。

別の実行が同じメッセージを拾います。

これが二重処理の正体です。

だから「短縮」は、ほぼ罠です。

6倍が、ちょうどいい落としどころです。

次に、行列の読み方です。

ApproximateAgeOfOldestMessageが高止まりしている。

それでもLambdaのエラーは無く、全件が正常に処理されている。

これは故障やない。

消費が追いついていないだけです。

即答は、Lambdaの同時実行数の上限引き上げです。

| 症状 | 読み方 |
| --- | --- |
| 行列が伸びる＋エラー無し | 処理能力の不足 |
| 行列が伸びる＋エラー有り | 処理そのものの失敗 |
| メッセージが2回処理される | 可視性タイムアウト不足 |

「エラー無し」の一文で、障害系の道具は全部切れます。

DLQは失敗したメッセージの行き先です。

エラーが無ければ、DLQは無関係です。

FIFO化も、並列性が下がるので逆方向です。

:::message
関数のタイムアウトは、可視性タイムアウト以下でなければいけません。
Lambdaはイベントソースマッピングの作成時にこれを検証し、超えているとエラーになります。
:::

## 問題3：毒メッセージとDLQ ― 隔離牢の使い方

**引き金**：「無効なメッセージが何度も再試行」「正常な処理まで遅れる」。

何度やっても成功しないメッセージがあります。

これを毒メッセージと呼びます。

放っておくと、正常なメッセージまで巻き添えになります。

即答は、DLQへの自動退避です。

送信元のキューにリドライブポリシーを付けます。

受信回数が上限を超えたら、DLQへ送ります。

| 設定 | 内容 |
| --- | --- |
| リドライブポリシー | 送信元キューに付ける |
| maxReceiveCount | 上限の受信回数 |
| DLQ | 退避先のキュー |

公式は、maxReceiveCountを5以上にするよう推奨しています。

数回は再試行して、それでもダメなら隔離する。

このバランスが大事です。

| ステップ | 内容 |
| --- | --- |
| **最終文** | 聞かれているのは「毒の隔離方法」です |
| **制約** | 決め手は「何度も再試行」「正常まで遅延」 |
| **違反スキャン** | 「タイムアウト延長」は毒を治さない → 消去 |

タイムアウトの延長では、毒は成功しません。

バッチサイズを増やすと、巻き添えが増えるだけです。

バッチウィンドウを増やすと、遅延が悪化します。

3つとも、方向がズレています。

バッチ処理には、もう1つの罠があります。

バッチの一部だけが失敗すると、全部が再試行されます。

成功した分まで、もう一度処理される。

これを防ぐのが、部分バッチ応答です。

失敗したメッセージだけを返すと、成功分は削除されます。

:::details 部分バッチ応答の使いどころ
- バッチの一部だけ失敗する → 部分バッチ応答で成功分を削除
- バッチ全体が失敗する → 可視性タイムアウト後に全件が再表示
:::

## 問題4：1MB超のペイロード ― S3参照渡しで運ぶ

**引き金**：「256KB超のペイロード」。

大きい荷物は、キューに直積みしません。

S3に置いて、参照だけを運びます。

これがS3参照渡しの型です。

| 荷物の大きさ | 運び方 |
| --- | --- |
| 1MBまで | そのままメッセージに入れる |
| 1MB超 | S3に置いて参照だけ送る |

SQSのメッセージ上限は、2025年8月に1MiBへ緩和されました。

それまでは256KBが上限でした。

Lambdaの非同期呼び出しも、2025年10月に1MBへ緩和されました。

同期呼び出しの上限は6MBのままです。

| 経路 | 現在の上限 |
| --- | --- |
| SQSメッセージ | 1MiB |
| Lambda非同期呼び出し | 1MB |
| Lambda同期呼び出し | 6MB |

1MBを超えたら、S3参照渡しです。

SQS Extended Client Libraryを使えば、最大2GBまで運べます。

| ステップ | 内容 |
| --- | --- |
| **最終文** | 聞かれているのは「大きい荷物の運び方」です |
| **制約** | 決め手は「256KB超」「ペイロード」という数字 |
| **違反スキャン** | 「分割して送る」は手作り配管 → 消去 |

:::message
原典のドリルは「256KB超 → S3参照渡し」でした。
2025年の上限緩和で、SQSとLambda非同期呼び出しは1MBまで入るようになりました。
反射の核は「大きい荷物はキューに直積みしない」です。
数字だけ、1MBで覚え直してください。
:::
